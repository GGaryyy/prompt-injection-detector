# OOD Benchmark 中文摘要 — 2026-07-28/29

> 英文完整版:[ood_benchmark_2026-07-28.md](ood_benchmark_2026-07-28.md)
> 這份是給自己看的版本,重點在「我們做了什麼、發現什麼、為什麼重要」。

## 一句話

`OVERVIEW.md` 一直寫著「in-distribution only」這個限制,但從來沒有數字。這次把那句空話換成量測結果,而量測過程本身翻出了三件原本不知道的事。

## 為什麼要做

一個沒有數字的限制**是不可否證的**。它讀起來像自覺,但撐不過任何追問:

> 面試官:「0.97 F1 對真實新型攻擊撐得住嗎?」
> 舊答法:「不行,那是同分佈測試。」
> 面試官:「掉多少?」
> 舊答法:(沒有)

## 怎麼做的

核心原則只有一條:**量測,不修理**。

- 用凍結的 model artifact,**不重訓、不調 threshold、不調權重**
- 權重與 threshold 從 `src/detector.py` **import 進來**,不是複製一份 —— 並且有測試斷言它們是同一個物件。這樣 benchmark 不可能悄悄評到一個跟實際上線不同的設定
- holdout 資料集與訓練集**完全隔離**,而且用測試釘住

最後一點不是形式主義。發現時 `wildjailbreak` 的 loader **已經掛在訓練 registry 裡**,只因為沒人下載過那份資料才逃過污染。任何人跑一次 `build_dataset.py`,holdout 就會被吃進訓練集,而 benchmark 會照樣吐出一個看起來很合理的數字,**沒有任何錯誤訊息**。

## 三個發現

### 1. 掉幅:recall 0.960 → 0.198

| 資料集 | Recall | 誤報率 | AUC |
|---|---|---|---|
| 分布內(已遮蔽自匹配) | 0.9597 | 0.0050 | — |
| deepset(沒見過的攻擊) | **0.1977** | 0.0000 | 0.838 |
| alpaca(沒見過的良性) | — | **0.0380** | — |

但**這不是「模型看不懂」**。AUC 還有 0.838,代表分數排序仍然正確;把 threshold 調到 0.20 就回到 F1 0.722。所以問題是 **0.5 這個門檻對新分佈不適用**,是校準失敗,不是表徵失敗 —— 兩者的修法完全不同。

### 2. similarity 層從來沒有鑑別力(原假說被推翻)

原本的假說是「similarity 層在 OOD 上會崩掉」,因為它比對的是訓練正樣本本身。實測結果更糟:

| | 正樣本 | 負樣本 | 差距 |
|---|---|---|---|
| 分布內 | 0.858 | 0.539 | 0.319 |
| OOD | 0.626 | 0.572 | **0.054** |

差距 0.054 基本上是雜訊,而這一層佔 ensemble 權重 **20%**。

它在分布內看起來有用,是因為**評估有自匹配洩漏**:`known_attacks.jsonl` 收錄了全部正樣本(含測試集那份),所以每個測試攻擊都跟自己比中 cosine 1.0。遮蔽掉之後降到 0.858。

> **注意這裡的修法。** 有一版初稿建議「從源頭修:讓 `train.py` 只寫入訓練集的正樣本」。那是錯的,已刪除。正式環境的相似度語料**本來就該收錄所有已知攻擊** —— 語料越大越好,因為新進來的 request 永遠不在裡面。artifact 沒有洩漏,洩漏在「拿它來評估自己」這件事上,所以正確且完整的修法就是在評估時遮蔽自匹配。

### 3. `benchmark.json` 的 0.97 不是 ensemble 的分數

`scripts/train.py` 算 metric 用的 `y_pred` **只來自 classifier**,不是三層 ensemble。而 `OVERVIEW.md` 一直把這個數字當成「偵測器的效能」在講。

ensemble 在同一切分上是 F1 0.9723,所以**沒有灌水,但標錯了對象**。已在兩份 OVERVIEW 更正。

順帶一提:我自己寫的計畫裡「控制組要重現 0.9699」這個驗證條件本身就是錯的 —— 那兩個數字本來就在量不同的東西。報告裡照實記下來,沒有假裝重現成功。

## Paraphrase 探針(另一條線)

換資料集測的是「能不能泛化到別的分佈」;改寫測的是「學會攻擊,還是背下了字面」。兩者是不同的失效模式。

| | Recall | rule | classifier | similarity |
|---|---|---|---|---|
| 原文 | 0.9650 | 0.1600 | 0.9529 | 0.8567 |
| 改寫後 | 0.9150 | 0.0270 | 0.8914 | 0.7971 |
| 變化 | −5.0pp | **−83%** | −6.5% | −7.0% |

兩組都把「該筆 prompt 的來源攻擊」從 similarity 層排除(`src/eval_masking.py`,各遮掉 200/200)。不遮的話原文會跟自己 cosine 1.0,那個 recall 量到的是「在不在語料庫裡」,不是偵測能力。

rule 層被同義詞替換幾乎抹平,classifier 幾乎不動。

**這是下界不是測量值** —— 規則式改寫在字面上離原文很近,embedding 移動的幅度比真人重寫或 LLM 改寫小得多。這個但書寫在腳本的 module docstring 裡,所以數字不可能被脫離前提引用。

> **2026-07-29 修訂。** 上表取代先前未遮蔽的版本(原文 recall 0.9750、similarity 1.0000;變化 −4.5pp / −10%)。其中 similarity 的跌幅是假的:大部分來自原文那組從自我匹配掉下來,而不是改寫後真的離語料庫變遠。這個 bug 是 code review 抓到的 —— 跟 `scripts/eval_ood.py` 早先修掉的是同一個洩漏,只是沒有一併套到探針上。

與 OOD 結果合起來的圖像:**classifier 對「認識的攻擊的改寫」泛化得不錯,對「不同分佈的攻擊」不行。**

## 過程中我自己犯的兩個錯

值得記下來,因為它們正是這整件事要消滅的那類數字:

1. **自匹配洩漏**(High)—— 第一版沒遮蔽,similarity 層報出完美的 1.0。這個錯會改變**結論**而不只是數字:那一層會從「很強」被誤讀成真的很強。
2. **alpaca 報 `F1 = 0.0000`**(High)—— alpaca 全是負樣本,P/R/F1 在單一類別下是退化值。這個數字讀起來像全面失敗,實際上該報的是 3.8% 誤報率。

兩個都是看第一次跑的輸出才發現的,**不是測試抓到的**。事後補了測試釘住。這說明一件事:當初寫的測試把 registry 不變式顧得很好,把 metric 語義完全沒顧到。

## 後續(**刻意不做**)

| 項目 | 為什麼不做 |
|---|---|
| similarity 層該不該保留 20% 權重 | 一旦為了救 OOD 分數調權重,holdout 就變成第二個訓練集,這份 benchmark 的價值歸零 |
| threshold 重新校準 | 同上 |
| 補跑 wildjailbreak | 需要 `huggingface-cli login` |

## Holdout 與訓練語料的重疊

Holdout 是不遮蔽計分的,而這只有在它們真的沒被看過時才成立。實測(2026-07-29,`output/benchmark_ood.json` 的 `n_verbatim_in_corpus`):正規化比對下,deepset **0/662**、Alpaca **0/3000** 逐字出現在 `known_attacks.jsonl` 裡。所以上面的 OOD 數字沒有「因為在語料庫裡才被抓到」的污染。這個數字現在每次跑都會報,不再是假設。

## 最大的限制(要主動講,別等被戳)

**只有一個 holdout 攻擊來源,263 筆正樣本。** WildJailbreak 需要 HF 登入沒跑到,所以攻擊側只靠 deepset 一個資料集。

這代表現在**還分不出**「OOD 就是會掉」和「deepset 這個資料集特別難」。0.198 這個數字在補上第二個來源之前,不能當成通則。這個限制寫進了報告、兩份 OVERVIEW 和面試筆記。
